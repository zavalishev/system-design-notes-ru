# Глава 11: Проектирование ленты новостей (News Feed System)

## Введение
**Лента новостей (news feed)** — это постоянно обновляемый список публикаций (статусов, фотографий, видео и ссылок) от связей пользователя. Примеры: лента новостей Facebook, лента Instagram и таймлайн Twitter. В этой главе мы разбираем проектирование масштабируемой системы ленты новостей.

---

## Шаг 1: Понимание задачи

### Требования
1. **Платформа:** система поддерживает и веб, и мобильные приложения.
2. **Функциональность:**
   - Пользователи могут публиковать посты.
   - Пользователи видят посты друзей в своей ленте новостей.
3. **Сортировка:** для простоты лента сортируется в **обратном хронологическом порядке**.
4. **Масштаб:**
   - У пользователя может быть до 5 000 друзей.
   - 10 миллионов активных пользователей в день (DAU).
   - Лента может содержать текст, изображения и видео.

---

## Шаг 2: Высокоуровневый дизайн

### Обзор
Дизайн включает два основных потока:
1. **Публикация в ленту:** пользователь публикует пост, который записывается в базу данных и распространяется в ленты его друзей.
2. **Построение ленты новостей:** пользователь получает свою ленту как агрегацию постов друзей в обратном хронологическом порядке.

---

### API ленты новостей
1. **API публикации в ленту:**
   - **Эндпоинт:** `POST /v1/me/feed`
   - **Параметры:** `content` (текст поста) и `auth_token` (аутентификация).

2. **API получения ленты новостей:**
   - **Эндпоинт:** `GET /v1/me/feed`
   - **Параметры:** `auth_token` (аутентификация).

## Шаг 3: Детальный разбор дизайна

### Публикация в ленту: подробности
1. **Веб-серверы:**
   - Аутентифицируют пользователей по `auth_token`.
   - Применяют ограничение частоты запросов (rate limiting) для защиты от спама.

2. **Сервис рассылки (fanout service):**
   - **Рассылка при записи (fanout on write):** посты проталкиваются в ленты друзей в момент публикации.
     - **Плюсы:** обновления в реальном времени, быстрое получение ленты.
     - **Минусы:** ресурсоёмко для пользователей с большим числом друзей.
   - **Рассылка при чтении (fanout on read):** посты подтягиваются в момент чтения.
     - **Плюсы:** эффективно для неактивных пользователей.
     - **Минусы:** более медленное получение ленты.
   - **Гибридный подход:** push-модель для большинства пользователей и pull-модель для пользователей с огромным числом связей (например, знаменитостей).

        <img src="./images/feed-publishing-deep-dive.png" alt="Публикация в ленту: подробности" width="500">

    **Сервис рассылки** работает следующим образом:

    1. **Получение идентификаторов друзей:** список друзей извлекается из графовой базы данных.
    2. **Фильтрация друзей через кеш:** обращаемся к настройкам пользователя в кеше, чтобы исключить отдельных друзей (например, заглушённых или согласно настройкам выборочного доступа).
    3. **Отправка в очередь сообщений:** отфильтрованный список друзей вместе с ID нового поста отправляется в очередь сообщений на обработку.
    4. **Воркеры рассылки (fanout workers):** воркеры забирают данные из очереди и обновляют кеш лент новостей. Для экономии памяти кеш хранит пары `<post_id, user_id>` вместо полных объектов пользователей и постов.
    5. **Сохранение в кеше ленты:** идентификаторы новых постов добавляются в кеши лент друзей. Настраиваемый лимит гарантирует, что хранятся только свежие посты, — большинство пользователей интересуется именно последним контентом, и это удерживает потребление памяти кеша в разумных пределах.

## Получение ленты новостей: подробности

### Архитектура кеша
Кеш делится на пять слоёв:
1. **Кеш ленты новостей:** хранит идентификаторы постов для быстрого доступа.
2. **Кеш контента:** хранит данные постов (популярные посты — в «горячем» кеше).
3. **Кеш социального графа:** хранит данные о связях пользователей.
4. **Кеш действий:** отслеживает действия пользователей (лайки, ответы, репосты).
5. **Кеш счётчиков:** ведёт счётчики лайков, ответов, подписчиков и т.д.

## Ключевые оптимизации

### Масштабирование
1. **Масштабирование базы данных:**
   - Горизонтальное масштабирование и шардирование.
   - Использование реплик для чтения при высоконагруженных запросах.
2. **Веб-слой без состояния:** веб-серверы остаются stateless, что позволяет масштабироваться горизонтально.

### Кеширование
1. Храним часто запрашиваемые данные в памяти.
2. Используем слои кеша, чтобы снизить задержку и нагрузку на базу данных.

### Надёжность
1. **Консистентное хеширование:** равномерно распределяем запросы между серверами.
2. **Очереди сообщений:** развязываем компоненты системы и буферизуем трафик.

### Мониторинг
1. Отслеживаем ключевые метрики: QPS (запросы в секунду) и задержку.
2. Мониторим долю попаданий в кеш и корректируем конфигурацию.
