# Глава 21: Агрегация событий кликов по рекламе

## Введение
**Цифровая реклама** — огромная индустрия, выросшая вместе с Facebook, YouTube, TikTok и другими платформами.

Поэтому отслеживание событий кликов по рекламе имеет большое значение. В этой главе мы разберём, как спроектировать систему **агрегации событий кликов по рекламе (ad click event aggregation)** в масштабах Facebook/Google.

В цифровой рекламе есть процесс под названием **торги в реальном времени (real-time bidding, RTB)**, в ходе которого покупаются и продаются рекламные места:

<div style="margin-left:3rem">
    <img src="./images/digital-advertising-example.png" alt="пример цифровой рекламы" width="500" />
</div>

Скорость RTB критична — весь процесс обычно укладывается в одну секунду.
Точность данных не менее важна, поскольку от неё зависит, сколько денег заплатят рекламодатели.

На основе агрегированных данных о кликах рекламодатели принимают решения — например, корректируют целевую аудиторию и ключевые слова.

### **Функциональные требования**
 - Агрегировать количество кликов по `ad_id` за последние Y минут
 - Каждую минуту возвращать топ-100 самых кликабельных `ad_id`
 - Поддерживать фильтрацию агрегации по разным атрибутам
 - Объём данных — в масштабах Facebook или Google

### **Нефункциональные требования**
 - Корректность результатов агрегации важна, поскольку они используются для RTB и биллинга рекламы
 - Корректная обработка запоздавших и дублирующихся событий
 - Надёжность — система должна быть устойчива к частичным отказам
 - Задержка — не более нескольких минут сквозной задержки

### **Прикидочные оценки**
 - 1 млрд DAU
 - Предположим, что пользователь кликает по одному объявлению в день -> 1 млрд кликов в день
 - QPS кликов = 10 000
 - Пиковый QPS в 5 раз выше = 50 000
 - Один клик занимает 0,1 KB. Суточная потребность в хранилище — 100 GB
 - Хранилище за месяц = 3 TB

## Шаг 2: Предложить высокоуровневый дизайн и согласовать его
В этом разделе мы обсудим дизайн API запросов, модель данных и высокоуровневую архитектуру.

### **Дизайн API запросов**
API — это контракт между клиентом и сервером. В нашем случае клиент — это пользователь дашборда: дата-сайентист/аналитик, рекламодатель и т.д.

Наши функциональные требования:
 - Агрегировать количество кликов по `ad_id` за последние Y минут
 - Вернуть топ-N самых кликабельных `ad_id` за последние M минут
 - Поддерживать фильтрацию агрегации по разным атрибутам

Для этого нам понадобятся два эндпоинта. Фильтрацию можно реализовать через query-параметры одного из них.

**Агрегированное количество кликов по ad_id за последние M минут**:

```
GET /v1/ads/{:ad_id}/aggregated_count
```

Query-параметры:
 - from — начальная минута. По умолчанию — сейчас минус 1 минута
 - to — конечная минута. По умолчанию — сейчас
 - filter — идентификатор стратегии фильтрации. Например, 001 означает «клики не из США».

Ответ:
 - ad_id — идентификатор объявления
 - count — агрегированное количество между начальной и конечной минутами

**Вернуть топ-N самых кликабельных ad_id за последние M минут**

```
GET /v1/ads/popular_ads
```

Query-параметры:
 - count — топ-N самых кликабельных объявлений
 - window — размер окна агрегации в минутах
 - filter — идентификатор стратегии фильтрации

Ответ:
 - список ad_id

### **Модель данных**
В нашей системе есть сырые (raw) и агрегированные данные.

Сырые данные выглядят так:

```
[AdClickEvent] ad001, 2021-01-01 00:00:01, user 1, 207.148.22.22, USA
```

Вот пример в структурированном виде:
| ad_id | click_timestamp     | user  | ip            | country |
|-------|---------------------|-------|---------------|---------|
| ad001 | 2021-01-01 00:00:01 | user1 | 207.148.22.22 | USA     |
| ad001 | 2021-01-01 00:00:02 | user1 | 207.148.22.22 | USA     |
| ad002 | 2021-01-01 00:00:02 | user2 | 209.153.56.11 | USA     |

А вот агрегированная версия:
| ad_id | click_minute | filter_id | count |
|-------|--------------|-----------|-------|
| ad001 | 202101010000 | 0012      | 2     |
| ad001 | 202101010000 | 0023      | 3     |
| ad001 | 202101010001 | 0012      | 1     |
| ad001 | 202101010001 | 0023      | 6     |

Поле `filter_id` помогает нам реализовать требования к фильтрации.
| filter_id | region | IP        | user_id |
|-----------|--------|-----------|---------|
| 0012      | US     | *         | *       |
| 0013      | *      | 123.1.2.3 | *       |

Чтобы быстро возвращать топ-N самых кликабельных объявлений за последние M минут, мы также будем поддерживать такую структуру:
| most_clicked_ads   |           |                                                       |
|--------------------|-----------|-------------------------------------------------------|
| window_size        | integer   | Размер окна агрегации (M) в минутах                   |
| update_time_minute | timestamp | Время последнего обновления (с точностью до минуты)   |
| most_clicked_ads   | array     | Список ID объявлений в формате JSON.                  |

Каковы плюсы и минусы хранения сырых данных по сравнению с агрегированными?
 - Сырые данные позволяют работать с полным набором данных, поддерживают фильтрацию и пересчёт
 - Агрегированные данные, напротив, дают меньший объём и более быстрые запросы
 - Сырые данные означают более крупное хранилище и более медленные запросы
 - Агрегированные данные — производные, поэтому часть информации при агрегации теряется.

В нашем дизайне мы будем комбинировать оба подхода:
 - Сырые данные полезно хранить для отладки. Если в агрегации обнаружится ошибка, мы сможем найти её и пересчитать данные задним числом (backfill).
 - Агрегированные данные тоже нужно хранить — для быстрых запросов.
 - Сырые данные можно держать в холодном хранилище, чтобы не переплачивать за хранение.

При выборе базы данных нужно учесть несколько факторов:
 - Как выглядят данные? Они реляционные, документные или бинарные (blob)?
 - Нагрузка преимущественно на чтение, на запись или смешанная?
 - Нужны ли транзакции?
 - Опираются ли запросы на OLAP-функции вроде SUM и COUNT?

Для сырых данных средний QPS — 10 тыс., пиковый — 50 тыс., так что система нагружена на запись.
Чтение при этом редкое: сырые данные в основном служат резервной копией на случай проблем.

Реляционные базы справятся с задачей, но масштабировать запись в них непросто.
Как альтернативу можно использовать Cassandra или InfluxDB — у них лучше нативная поддержка тяжёлых нагрузок на запись.

Ещё один вариант — Amazon S3 с колоночным форматом данных вроде ORC, Parquet или AVRO. Поскольку такая конфигурация нам менее знакома, остановимся на Cassandra.

Для агрегированных данных нагрузка тяжёлая и на чтение, и на запись: агрегированные данные постоянно запрашиваются для дашбордов и оповещений.
Запись тоже интенсивная — сервис агрегации каждую минуту агрегирует и записывает данные.
Поэтому здесь мы тоже используем то же хранилище (Cassandra).

Узел map отвечает за чтение из источника данных, а затем за фильтрацию и преобразование данных.

Однако узел map даёт возможность очистить или преобразовать данные перед дальнейшей обработкой.

Узел aggregate каждую минуту подсчитывает события кликов по `ad_id` в памяти.

В DAG-модели промежуточные данные хранятся в памяти, а узлы обмениваются между собой по TCP или через разделяемую память.

У подхода следующие преимущества:
 - Прост в понимании и реализации
 - Существующий сервис агрегации можно переиспользовать для добавления новых измерений в схему «звезда».
 - Доступ к данным по критериям фильтрации быстрый, так как результаты вычислены заранее

Ограничение подхода — он порождает гораздо больше корзин (buckets) и записей, особенно при большом числе критериев фильтрации.

## Шаг 3: Детальное проектирование
Углубимся в некоторые наиболее интересные темы.

### **Потоковая обработка vs. пакетная**
Предложенная нами высокоуровневая архитектура — разновидность системы потоковой обработки.
Вот сравнение трёх типов систем:
|                         | Сервисы (онлайн-система)         | Пакетная система (офлайн-система)                          | Потоковая система (система, близкая к реальному времени) |
|-------------------------|----------------------------------|------------------------------------------------------------|----------------------------------------------------------|
| Отзывчивость            | Быстро отвечает клиенту          | Ответ клиенту не требуется                                 | Ответ клиенту не требуется                               |
| Вход                    | Запросы пользователей            | Ограниченный вход конечного размера. Большой объём данных  | Вход не имеет границ (бесконечные потоки)                |
| Выход                   | Ответы клиентам                  | Материализованные представления, агрегированные метрики и т.д. | Материализованные представления, агрегированные метрики и т.д. |
| Измерение производительности | Доступность, задержка       | Пропускная способность                                     | Пропускная способность, задержка                         |
| Пример                  | Интернет-магазин                 | MapReduce                                                  | Flink [13]                                               |

В нашем дизайне мы использовали смесь пакетной и потоковой обработки.

Потоковую обработку мы применили для обработки данных по мере поступления и получения агрегированных результатов почти в реальном времени.
Пакетную же — для резервного копирования исторических данных.

Система, в которой одновременно существуют два пути обработки — пакетный и потоковый, — называется лямбда-архитектурой (lambda).
Её недостаток в том, что приходится поддерживать два пути обработки с двумя разными кодовыми базами.

Альтернатива — каппа-архитектура (kappa), которая объединяет пакетную и потоковую обработку в одном пути.
Ключевая идея — использовать единственный движок потоковой обработки.

Когда нам нужно пересчитать агрегированные данные — например, из-за серьёзной ошибки в логике агрегации, — мы можем выполнить пересчёт из хранимых сырых данных.

 - Агрегированные результаты отправляются во вторую очередь сообщений, после чего мы обновляем результаты в базе агрегированных данных.

### **Время**
Для агрегации нам нужна временная метка. Она может формироваться в двух местах:
 - время события (event time) — момент клика по рекламе
 - время обработки (processing time) — системное время сервера в момент обработки события

Из-за асинхронной обработки (очереди сообщений) и сетевых задержек разница между временем события и временем обработки может быть существенной.
 - Если использовать время обработки, результаты агрегации могут быть неточными
 - Если использовать время события, придётся иметь дело с запоздавшими событиями

Идеального решения нет, нужно взвешивать компромиссы:
|                  | Плюсы                                   | Минусы                                                                                              |
|------------------|-----------------------------------------|-----------------------------------------------------------------------------------------------------|
| Время события    | Результаты агрегации точнее             | У клиентов может быть неверное время, либо метку могут сформировать злоумышленники                  |
| Время обработки  | Серверная метка времени надёжнее        | Метка неточна, если событие запоздало                                                               |

Поскольку точность данных важна, для агрегации мы будем использовать время события.

Чтобы смягчить проблему запоздавших событий, можно применить приём под названием «водяной знак» (watermark).

Однако если намеренно расширить окно агрегации, вероятность пропуска событий снизится.
Расширенная часть окна и называется «водяным знаком»:

<div style="margin-left:3rem">
    <img src="./images/watermark-2.png" alt="водяной знак 2" width="500" />
</div>

 - Короткий водяной знак повышает вероятность пропуска событий, но снижает задержку
 - Длинный водяной знак снижает вероятность пропуска событий, но увеличивает задержку

Вероятность пропуска событий сохраняется всегда, каким бы ни был размер водяного знака. Но нет смысла оптимизировать под столь маловероятные события.

Вместо этого такие расхождения можно устранять сверкой (reconciliation) в конце дня.

### **Гарантии доставки**
Поскольку агрегируемые данные будут использоваться для биллинга, точность данных — приоритет.

Поэтому нужно обсудить:
 - Как избежать обработки дублирующихся событий
 - Как гарантировать, что все события обработаны

Есть три варианта гарантий доставки: не более одного раза (at-most-once), не менее одного раза (at-least-once) и ровно один раз (exactly-once).

В большинстве случаев достаточно at-least-once, когда небольшое количество дубликатов допустимо.
Но для нашей системы это не так: расхождение в доли процента может обернуться миллионами долларов.
Поэтому нам понадобится семантика доставки exactly-once.

### **Дедупликация данных**
Одна из самых распространённых проблем качества данных — дубликаты.

Они могут возникать из самых разных источников:
 - На стороне клиента — клиент может отправить одно и то же событие несколько раз. Дубликаты, отправляемые со злым умыслом, лучше всего обрабатывать движком оценки рисков.
 - Отказ сервера — узел сервиса агрегации падает посреди агрегации, вышестоящий сервис не получает подтверждения и повторно отправляет событие.

### **Масштабирование системы**
Обсудим, как масштабировать систему по мере роста.

У нас три независимых компонента — очередь сообщений, сервис агрегации и база данных.
Поскольку они развязаны, масштабировать их можно независимо друг от друга.

Как масштабировать очередь сообщений:
 - Мы не ограничиваем производителей, поэтому их легко масштабировать
 - Потребителей можно масштабировать, объединяя их в группы потребителей и увеличивая их количество.
 - Чтобы это работало, нужно заранее создать достаточное количество партиций
 - Кроме того, ребалансировка потребителей может занять заметное время, когда их тысячи, поэтому делать её рекомендуется в часы низкой нагрузки
 - Также можно рассмотреть партиционирование топика по географии, например `topic_na`, `topic_eu` и т.д.

<div style="margin-left:3rem">

</div>

Как масштабировать сервис агрегации:

</div>

 - Узлы map-reduce легко масштабируются добавлением новых узлов
 - Пропускную способность сервиса агрегации можно увеличить за счёт многопоточности
 - Как альтернатива, можно использовать менеджеры ресурсов вроде Apache YARN для многопроцессной обработки
 - Вариант 1 проще, но вариант 2 чаще применяется на практике, поскольку лучше масштабируется

 - Если мы используем Cassandra, она нативно поддерживает горизонтальное масштабирование на основе консистентного хеширования

<div style="margin-left:3rem">

 - В примере выше узлы сервиса агрегации могут запросить дополнительные ресурсы через менеджер ресурсов
 - Менеджер ресурсов выделяет больше ресурсов, чтобы исходный узел не перегружался
 - Исходный узел разбивает события на 3 группы, и каждый узел агрегации обрабатывает по 100 событий
 - Результат записывается обратно в исходный узел агрегации

Альтернативные, более изощрённые способы борьбы с горячими точками:
 - Глобально-локальная агрегация (Global-Local Aggregation)
 - Split Distinct Aggregation

### **Мониторинг и корректность данных**
Поскольку агрегируемые данные критичны — они используются для биллинга, — очень важно наладить строгий мониторинг для контроля корректности.

Какие метрики стоит отслеживать:
 - **Задержка**: можно фиксировать временные метки разных событий, чтобы понимать сквозную задержку системы
 - **Размер очереди сообщений**: если размер очереди резко вырос, нужно добавить узлы агрегации. Поскольку Kafka реализована как распределённый журнал фиксации (commit log), вместо этого нужно отслеживать метрику отставания записей (records-lag).
 - **Системные ресурсы на узлах агрегации**: CPU, диск, JVM и т.д.

Также нужно реализовать процесс сверки — пакетную задачу, запускаемую в конце дня.
