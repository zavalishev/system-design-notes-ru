# Глава 13: Проектирование системы автодополнения поиска

## Введение
Автодополнение поиска (search autocomplete), также известное как typeahead или инкрементальный поиск, показывает пользователю подсказки в реальном времени по мере ввода текста в строку поиска. Система должна эффективно выдавать top-k релевантных и популярных подсказок, опираясь на историю поисковых запросов.

### Ключевые особенности
- Предлагать до **5 вариантов автодополнения**.
- Ранжирование по **популярности запроса** (частоте).
- Поддерживаются только **строчные буквы английского алфавита**.
- Быстрое время отклика (<100 ms) и масштабируемость.

---

## Шаг 1: Понимание задачи

### Требования
1. **Подсказки в реальном времени:** показывать релевантные совпадения по мере ввода.
2. **Top-k результатов:** возвращать до 5 результатов, отсортированных по популярности.
3. **Масштабируемость:** обслуживать **10 миллионов DAU** при пиковом QPS **48 000**.
4. **Высокая доступность:** переживать сбои без простоя системы.
5. **Рост данных:** поддерживать ежедневный прирост хранилища на **0.4 GB** за счёт новых запросов.

## Шаг 2: Высокоуровневый дизайн
На верхнем уровне система делится на два сервиса:
1. **Сервис сбора данных (data gathering service):**
    - Собирает пользовательские запросы и агрегирует их для анализа частотности в реальном времени.
    - Обработка в реальном времени непрактична для больших объёмов данных, но это хорошая отправная точка.


2. **Сервис запросов (query service):** возвращает top-k подсказок по вводу пользователя.

## Шаг 3: Детальное проектирование

### Структура данных trie
**Префиксное дерево (trie)** — древовидная структура данных для эффективного хранения и поиска строк запросов.

#### Ключевые особенности
1. **Компактное хранение:** префиксы представлены иерархически, что сводит к минимуму избыточность.
2. **Информация о частоте:** в каждом узле хранится популярность запросов.

4. **Шаги получения top-k самых популярных запросов**
   <div style="margin-left:3rem">
      <img src="./images/trie-structure.png" alt="Структура trie" width="500">
   </div>

    - Найти префикс
    - Обойти поддерево от узла префикса и собрать всех допустимых потомков
    - Отсортировать потомков и взять top-k


3. **Оптимизации:**
   - Кешировать top-k запросов в каждом узле, чтобы ускорить выборку и не обходить всё дерево целиком.

        <img src="./images/cached-trie.png" alt="Trie с кешем" width="600">

   - Ограничить длину префикса, чтобы сузить пространство поиска: пользователи редко набирают длинные поисковые запросы (скажем, больше 50 символов).

#### Операции над trie
1. **Создание:**
    - Дерево строится еженедельно на основе агрегированных данных о запросах.
    - Источник данных — аналитические логи / БД.
2. **Обновление:** в реальном времени обновляется редко; еженедельные обновления замещают старые данные.
3. **Удаление:**
      <div style="margin-left:3rem">
         <img src="./images/delete-kv.png" alt="Удаление из KV-хранилища" width="500">
      </div>

    - Фильтры убирают нежелательные или вредные подсказки (например, разжигание ненависти).
    - Наличие слоя фильтрации даёт гибкость: результаты можно убирать по разным правилам фильтрации.
    - Нежелательные подсказки физически удаляются из базы данных асинхронно.
    

---

### Процесс обработки запроса
1. **Поиск префикса:**
   - Найти узел префикса, соответствующий вводу пользователя.
   - Обойти поддерево и собрать допустимые подсказки.
2. **Сортировка top-k:**
   - Кешировать top-k подсказок в каждом узле, чтобы минимизировать накладные расходы на сортировку.
3. **Формирование ответа:**
   - Собирать результаты из закешированных данных, чтобы отвечать быстро.

---

### Оптимизации
1. **Кеш в каждом узле:**
   - Хранить top-k запросов, чтобы избежать лишних обходов дерева.
2. **Ограничение длины префикса:**
   - Ограничить длину префикса небольшим значением (например, 50 символов) для ускорения поиска.
3. **AJAX-запросы:**
   - Использовать лёгкие асинхронные запросы для получения ответов в реальном времени.
4. **Кеширование в браузере:**
   - Сохранять результаты автодополнения в кеше браузера для часто запрашиваемых терминов.

---

### Конвейер сбора данных
В высокоуровневом дизайне данные обновляются в реальном времени всякий раз, когда пользователь вводит поисковый запрос. Такой подход непрактичен.
- Пользователи могут вводить миллиарды запросов в день. Обновлять trie на каждый запрос невозможно.
- После построения дерева топовые подсказки меняются несильно.


#### Обновлённый дизайн

<div style="margin-left:3rem">
   <img src="./images/data-gathering-flow.png" alt="Обновлённый процесс сбора данных" width="600">
</div>

1. **Аналитические логи:**
   - Хранят сырые данные запросов в виде логов для еженедельной агрегации.
   - Логи только дописываются (append-only) и не индексируются.
2. **Агрегаторы:**
   - Преобразуют логи в таблицы частот, пригодные для построения trie.
   - Для приложений реального времени, таких как Twitter, данные агрегируются с более коротким интервалом.
   - В остальных случаях достаточно агрегировать данные реже, скажем раз в неделю.
3. **Воркеры:**
   - Асинхронные серверы, которые перестраивают trie и сохраняют его в постоянное хранилище.
4. **Варианты хранения:**
    - **Кеш trie (Trie Cache):** распределённая система кеширования, которая держит trie в памяти для быстрого чтения.
    - **БД trie (Trie DB):**
        1. **Документное хранилище (например, MongoDB):** поскольку новое дерево строится еженедельно, можно периодически делать его снимок, сериализовать и сохранять сериализованные данные в базе вроде MongoDB.
        2. **Key-value хранилище:**
            - Сопоставляет префиксы с данными узлов для быстрого доступа.
            - Каждый префикс в trie отображается в ключ хеш-таблицы.
            - Данные каждого узла trie отображаются в значение хеш-таблицы.

                <img src="./images/trie-db.png" alt="БД trie" width="600">
---

### Масштабируемость
1. **Шардирование:**
   - Распределять узлы trie по серверам на основе диапазонов префиксов (например, `a-m`, `n-z`).
   - Дополнительно шардировать внутри префиксов, чтобы сгладить неравномерное распределение (например, `aa-ag`, `ah-an`).
2. **Балансировка нагрузки:**
   <div style="margin-left:3rem">
      <img src="./images/sharding.png" alt="Шардирование" width="400">
   </div>

   - Использовать менеджер карты шардов (shard map manager), чтобы направлять запросы на нужный сервер.

## Шаг 4: Дополнительные возможности

### Поддержка нескольких языков
1. **Символы Unicode:** использовать Unicode для поддержки неанглийских языков.
2. **Отдельные trie для стран:** строить отдельные деревья для разных стран или регионов.

### Трендовые запросы
- Реагировать на события в реальном времени, динамически обновляя узлы trie или придавая больший вес недавним запросам.
