# Глава 7: Проектирование генератора уникальных идентификаторов в распределённых системах

## Введение
Эта глава посвящена задаче проектирования **генератора уникальных идентификаторов** (unique ID generator) для распределённых систем. Традиционные автоинкрементные ключи не подходят для распределённых сред из-за проблем с масштабируемостью и синхронизацией. Основное внимание уделяется созданию уникальных, сортируемых 64-битных числовых идентификаторов, отвечающих следующим требованиям:
- Идентификаторы должны быть **уникальными** и **упорядоченными по дате**.
- Идентификаторы должны умещаться в **64 бита**.
- Система должна генерировать **более 10 000 идентификаторов в секунду**.

---

## Шаг 1: Понимание задачи
### Базовые требования
- Идентификаторы должны быть уникальными, числовыми и умещаться в 64 бита.
- Идентификаторы возрастают со временем, но не обязательно строго на `+1`.
- Идентификаторы должны сортироваться по дате.
- Система должна выдерживать высокую пропускную способность (10 000 ID/с).

---

## Шаг 2: Варианты высокоуровневого дизайна
### 1. Репликация с несколькими мастерами (multi-master replication)
- **Подход:** использовать `auto_increment` базы данных с шагом инкремента (например, `+k` при k серверах).

    <p align="left">
    <img src="./images/multi-master.png"  alt="Несколько мастеров" width="400">
    </p>

- **Недостатки:**
  - Сложно масштабировать между дата-центрами.
  - Идентификаторы не всегда возрастают со временем.
  - Проблемы с масштабированием при добавлении и удалении серверов.

### 2. UUID (Universally Unique Identifier)
- **Подход:** 
    - Генерировать 128-битные уникальные идентификаторы независимо на каждом сервере с помощью UUID.
    - UUID можно генерировать независимо, без какой-либо координации между серверами.

        <p align="left">
        <img src="./images/uuid.png"  alt="Генератор UUID" width="600">
        </p>

- **Преимущества:**
  - Координация между серверами не нужна.
  - Легко масштабируется вместе с веб-серверами.
- **Недостатки:**
  - Превышает требование в 64 бита.
  - Идентификаторы не сортируются по времени и могут быть нечисловыми.


### 3. Сервер тикетов (ticket server)
- **Подход:** использовать централизованный сервер базы данных для инкремента и выдачи идентификаторов.

    <p align="left">
    <img src="./images/ticket-server.png"  alt="Сервер тикетов" width="500">
    </p>

- **Преимущества:**
  - Простота реализации для небольших систем.
  - Генерирует числовые идентификаторы.
- **Недостатки:**
  - Единая точка отказа.
  - Сложности с синхронизацией в конфигурациях с несколькими серверами.

### 4. Подход Twitter Snowflake
- **Подход:** 

    <div style="margin-left:3rem">
      <img src="./images/twitter-snowflake.png"  alt="Подход Snowflake" width="500">
    </div>
    <div style="margin-left:3rem">
      <img src="./images/snowflake-id-breakdown.png"  alt="Структура идентификатора Snowflake" width="500">
    </div>

    - Разбить идентификатор на секции, чтобы обеспечить уникальность и масштабируемость.
    - **Знаковый бит (1 бит):** всегда `0`; потенциально может использоваться для различения знаковых и беззнаковых чисел.
    - **Метка времени (41 бит):** миллисекунды с момента пользовательской эпохи (по умолчанию у Twitter это `1288834974657`, что соответствует 04 ноября 2010 года, 01:42:54 UTC). Обеспечивает упорядоченность идентификаторов по времени.
    - **Идентификатор дата-центра (5 бит):** позволяет адресовать до `2^5 = 32` дата-центров.
    - **Идентификатор машины (5 бит):** позволяет адресовать до `2^5 = 32` машин в каждом дата-центре.
    - **Порядковый номер (12 бит):** отслеживает идентификаторы, сгенерированные на машине в пределах одной миллисекунды, поддерживая до `2^12 = 4096` идентификаторов в миллисекунду. Счётчик сбрасывается в `0` каждую миллисекунду.



- **Преимущества:**
    - **Масштабируемость:** выдерживает более 10 000 идентификаторов в секунду на нескольких серверах.
    - **Упорядоченность по времени:** идентификаторы можно сортировать по времени.
    - **Децентрализация:** нет единой точки отказа.


## Шаг 4: Дополнительные соображения
### 1. Синхронизация часов
- **Проблема:** генерация идентификаторов предполагает, что часы на серверах синхронизированы.
- **Решение:** использовать **протокол сетевого времени (NTP)**, чтобы минимизировать расхождение.

### 2. Настройка длины секций
- Подбирайте размеры секций (например, меньше бит на порядковый номер, больше — на метку времени) в зависимости от сценария использования.

### 3. Высокая доступность
- Генераторы идентификаторов критически важны и должны быть отказоустойчивыми.
- Продумайте резервирование и механизмы аварийного переключения (failover).
