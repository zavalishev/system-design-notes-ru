# Глава 15: Проектирование Google Drive

## Введение
Google Drive — облачный сервис хранения и синхронизации файлов, который позволяет пользователям хранить файлы, обращаться к ним и делиться ими с разных устройств. В этой главе обсуждается проектирование масштабируемой системы со следующими возможностями:
- **Загрузка и скачивание файлов**
- **Синхронизация файлов между устройствами**
- **Совместный доступ к файлам**
- **История версий файлов**
- **Уведомления об изменениях, удалениях и предоставлении доступа**

---

## Шаг 1: Понимание задачи

### Ключевые требования
#### Функциональные требования:
- Загрузка и скачивание файлов.
- Синхронизация файлов между несколькими устройствами.
- Хранение версий файлов.
- Совместный доступ к файлам с разграничением прав.
- Отправка уведомлений при изменении, удалении файлов и предоставлении доступа.

#### Нефункциональные требования:
- **Надёжность:** потеря данных недопустима.
- **Быстрая синхронизация:** не заставлять пользователя ждать при задержках синхронизации.
- **Экономия трафика:** минимизировать лишний расход данных.
- **Масштабируемость:** обслуживать 10 миллионов активных пользователей в день (DAU).
- **Высокая доступность:** бесперебойная работа при сбоях серверов или проблемах с сетью.

### Ограничения и допущения
- Пользователи получают **10 GB бесплатного пространства**.
- Максимальный размер файла: **10 GB**.
- Средний размер загружаемого файла: **500 KB**.
- Частота загрузки: **2 файла в день на пользователя**.
- Общий требуемый объём хранилища: **500 PB**.

## Шаг 2: Высокоуровневый дизайн
### Конфигурация с одним сервером
Базовая конфигурация включает:
1. **Веб-сервер:** обрабатывает загрузку и скачивание.
2. **База метаданных:** хранит метаданные — данные пользователей, информацию для входа, сведения о файлах.
3. **Каталог хранения:** содержит файлы, организованные по пространствам имён (namespaces).


<div style="margin-left:3rem">
    <img src="./images/namespaces.png" alt="Пространства имён" width="400" />
</div>

- Настраиваются веб-сервер и каталог drive/, который служит корневым каталогом для загруженных файлов.
- Внутри каталога drive/ находится набор каталогов — пространств имён.
- Каждое пространство имён содержит все загруженные файлы соответствующего пользователя.
- Любой файл или папку можно однозначно идентифицировать, соединив пространство имён и относительный путь.


Такой дизайн годится как отправная точка, но не подходит для масштабирования.

#### API
1. **Загрузка файла в Google Drive:** поддерживаются два типа загрузки
    - Простая загрузка: используется для файлов небольшого размера.
    - Возобновляемая загрузка (resumable upload):
        - Эндпоинт: https://api.example.com/files/upload?uploadType=resumable
        - Отправить первоначальный запрос и получить URL для возобновляемой загрузки.
        - Загружать данные и отслеживать состояние загрузки.
        - Если загрузка прервалась — возобновить её.
2. **Скачивание файла из Google Drive:** чтобы скачать файл
    -  Эндпоинт: https://api.example.com/files/download
3. **Получение версий файла:**
    - Эндпоинт: https://api.example.com/files/list_revisions

### Переход к распределённой системе

#### Улучшения:
1. **Шардирование:** распределить хранилище по серверам на основе `user_id`.
2. **Amazon S3:** использовать S3 для масштабируемого и избыточного хранения файлов с межрегиональной репликацией.

    <img src="./images/replication.png" alt="Репликация" width="600" />
     
3. **Балансировщик нагрузки:** распределяет трафик между несколькими веб-серверами.
4. **Репликация базы метаданных:** обеспечить доступность за счёт шардирования и репликации базы данных.


#### Конфликты синхронизации:
В крупной системе хранения вроде Google Drive конфликты синхронизации время от времени неизбежны.
Конфликт возникает, когда два пользователя одновременно изменяют один и тот же файл или папку.

<div style="margin-left:5rem">
<img src="./images/sync-conflicts.png" alt="Конфликты синхронизации" width="600" />
</div>

- В примере пользователь 1 и пользователь 2 пытаются одновременно обновить один и тот же файл, но система первым обрабатывает файл пользователя 1.
- Обновление пользователя 1 проходит успешно, а пользователь 2 получает конфликт синхронизации.
- Система показывает обе копии файла: локальную копию пользователя 2 и последнюю версию с сервера.
- Пользователь 2 может либо объединить оба файла, либо заменить одну версию другой.

### Улучшенный дизайн
<div style="margin-left:5rem">
<img src="./images/high-level-design.png" alt="Высокоуровневый дизайн" width="500" />
</div>

1. **Взаимодействие с пользователем:** пользователи работают с приложением через браузер или мобильное приложение.

2. **Блочные серверы (block servers):**
   - Файлы разбиваются на **блоки по 4 MB** (максимальный размер), каждому присваивается уникальный хеш.
   - Блоки независимо друг от друга сохраняются в облачном хранилище (например, Amazon S3).
   - Для восстановления файла блоки соединяются в определённом порядке.

3. **Облачное хранилище:** блоки хранятся в облаке ради масштабируемости и избыточности.

4. **Холодное хранилище:** неактивные файлы переносятся в холодное хранилище для снижения затрат.

5. **Балансировщик нагрузки:** равномерно распределяет запросы между API-серверами для эффективной работы.

6. **API-серверы:**
   - Отвечают за аутентификацию пользователей, управление профилями и обновление метаданных файлов.
   - Обслуживают все процессы, не связанные с загрузкой файлов.

7. **База метаданных и кеш:**
   - Хранит метаданные о пользователях, файлах, блоках и версиях.
   - Часто запрашиваемые метаданные кешируются для ускорения доступа.

8. **Сервис уведомлений:**
   - Система по модели **издатель/подписчик (publisher/subscriber)**, уведомляющая клиентов об изменениях файлов (добавление, изменение, удаление).
   - Гарантирует, что клиенты смогут получить последние обновления.

9. **Очередь офлайн-резервирования:** временно хранит информацию об изменениях файлов для офлайн-клиентов, чтобы они синхронизировались после выхода в сеть.

### Процесс загрузки файла

1. **Загрузка файла:**
   - Блочный сервер разбивает файл на блоки, сжимает и шифрует их.
   - Блоки отправляются на блочные серверы и сохраняются в S3.
2. **Загрузка метаданных:**
   - Клиент отправляет метаданные на API-сервер.
   - Метаданные сохраняются в базе со статусом `pending`.
3. **Завершение:**
   - S3 вызывает колбэк, который меняет статус файла на `uploaded`.
   - Сервис уведомлений оповещает нужных пользователей.

### Синхронизация файлов
1. **Дельта-синхронизация (delta sync):** передавать только изменённые блоки, а не файл целиком.

    <div style="margin-left:2rem">

2. **Сжатие:** блоки сжимаются алгоритмами, подобранными под тип файла.
3. **Разрешение конфликтов:**
   - Побеждает версия, обработанная первой.
   - Конфликтующие версии сохраняются отдельно, чтобы пользователь разрешил конфликт сам.

### Процесс скачивания файла
Скачивание запускается, когда файл добавлен или изменён на другом устройстве. Клиент может узнать об этом двумя способами:
- Если клиент A в сети в момент изменения файла другим клиентом, его оповестит сервис уведомлений.
- Если клиент A офлайн в момент изменения файла другим клиентом, данные сохраняются в кеш. Когда офлайн-клиент снова выходит в сеть, он подтягивает последние изменения.

Узнав об изменении файла, клиент сначала запрашивает метаданные через API-серверы, а затем скачивает блоки и восстанавливает файл.

1. **Триггер:** сервис уведомлений сообщает клиенту об обновлении файла.
2. **Получение метаданных:** клиент получает обновлённые метаданные через API.
3. **Скачивание блоков:** клиент скачивает обновлённые блоки с блочных серверов и восстанавливает файл.

### Сервис уведомлений
1. **Назначение:** держать клиентов в курсе изменений файлов.
2. **Механизм:** использует **длинные опросы (long polling)** для асинхронных уведомлений.
3. **Пример:** при добавлении, изменении или удалении файла уведомления рассылаются всем заинтересованным клиентам.


---

### Оптимизация хранилища
1. **Дедупликация:** удалять дублирующиеся блоки на уровне аккаунта, сравнивая их по хешам.
2. **Стратегия версионирования:**
   - Ограничить число сохраняемых версий.
   - Для часто редактируемых файлов отдавать приоритет недавним версиям.
3. **Холодное хранилище:** переносить редко используемые файлы в более дешёвые хранилища (например, Amazon S3 Glacier).

---

### Обработка сбоев
1. **Сбой балансировщика нагрузки:** активируется резервный балансировщик.
2. **Сбой блочного сервера:** незавершённые задачи передаются другим серверам.
3. **Сбой базы метаданных:**
   - Повысить slave-узел до master.
   - Перенаправить трафик на оставшиеся реплики.
4. **Сбой облачного хранилища:** получать недоступные файлы из других регионов благодаря межрегиональной репликации.
5. **Сбой сервиса уведомлений:** клиенты переподключаются к другим серверам.
