# Глава 4: Проектирование ограничителя частоты запросов (Rate Limiter)

## Введение
В этой главе рассматривается проектирование и реализация ограничителя частоты запросов (rate limiter) — компонента системы, который контролирует интенсивность трафика от клиентов или сервисов. Ограничители частоты запросов необходимы, чтобы предотвращать злоупотребления, снижать расходы и поддерживать стабильность серверных ресурсов. Примеры применения: лимиты на публикацию постов, создание аккаунтов и получение бонусов.

## Преимущества ограничения частоты запросов
- **Защита от DoS-атак:** блокировка избыточных вызовов, чтобы не допустить исчерпания ресурсов.
- **Снижение затрат:** ограничение лишних запросов уменьшает расходы на серверы.
- **Защита от перегрузок:** отсев чрезмерных запросов стабилизирует работу серверов.

## Шаг 1: Понимание задачи
### Ключевые характеристики
- Ограничитель частоты запросов к API на стороне сервера.
- Поддержка нескольких правил троттлинга.
- Работа в крупных системах в распределённой среде.
- Возможность реализации как отдельным сервисом, так и кодом на уровне приложения.
- Уведомление пользователей о том, что их запросы ограничены.

### Требования
- Точное ограничение запросов.
- Минимальная задержка.
- Низкое потребление памяти.
- Возможность работы в распределённой среде.
- Понятная обработка исключений.
- Высокая отказоустойчивость.

## Шаг 3: Алгоритмы ограничения частоты запросов
### 1. Ведро с токенами (Token Bucket)
<div style="margin-left:2rem">
  <img src="./images/token-bucket.png"  alt="Алгоритм Token Bucket" width="550">
</div>

- **Описание:** токены добавляются в ведро с фиксированной скоростью; каждый запрос расходует один токен.
- **Параметры:** размер ведра и скорость пополнения.
- **Плюсы:** просто реализуется, экономит память, допускает всплески трафика.
- **Минусы:** требует аккуратной настройки параметров.



### 2. Дырявое ведро (Leaking Bucket)
<div style="margin-left:2rem">
  <img src="./images/leaking-bucket.png"  alt="Алгоритм Leaking Bucket" width="550">
</div>

- **Описание:** запросы обрабатываются с фиксированной скоростью через очередь FIFO.
- **Плюсы:** экономит память, стабильная скорость обработки на выходе.
- **Минусы:** при всплеске трафика свежие запросы могут надолго задержаться.
  

  Пример: https://github.com/uber-go/ratelimit



### 3. Счётчик с фиксированным окном (Fixed Window Counter)
<div style="margin-left:2rem">
  <img src="./images/fixed-window-counter.png"  alt="Счётчик с фиксированным окном" width="550">
</div>

- **Описание:** время делится на фиксированные интервалы, в каждом ведётся счётчик запросов.
- **Плюсы:** просто, эффективно для отдельных сценариев.
- **Минусы:** всплески трафика на границах окон могут превысить лимит.

- Резкий всплеск трафика на границе временных окон
может пропустить больше запросов, чем разрешено квотой.

  <img src="./images/fixed-window-issue.png"  alt="Проблема фиксированного окна" width="550">


### 4. Журнал скользящего окна (Sliding Window Log)
<div style="margin-left:2rem">
  <img src="./images/sliding-window-log.png"  alt="Журнал скользящего окна" width="550">
</div>

- **Описание:** хранит временные метки запросов, что даёт по-настоящему скользящее окно.
- **Плюсы:** точное ограничение частоты.
- **Минусы:** высокое потребление памяти.
  


### 5. Счётчик со скользящим окном (Sliding Window Counter)
<div style="margin-left:2rem">
  <img src="./images/sliding-window-counter.png"  alt="Счётчик со скользящим окном" width="550">
</div>

- **Описание:** объединяет подходы фиксированного окна и журнала скользящего окна, сглаживая всплески.
- **Плюсы:** экономит память, справляется со всплесками трафика.
- **Минусы:** приближённый расчёт, не абсолютно строгий.

## Дополнительные соображения
### Распределённая среда
- **Проблемы:** состояния гонки (race conditions), сложности синхронизации.
- **Решения:** блокировки, Lua-скрипты или отсортированные множества (sorted sets) в Redis. Централизованное хранилище данных для синхронизации.

### Оптимизация производительности
- Развёртывание в нескольких дата-центрах для снижения задержек.
- Модели согласованности в конечном счёте (eventual consistency) для синхронизации.

### Мониторинг
- Регулярная аналитика, чтобы убедиться в эффективности алгоритма и при необходимости корректировать правила.
