# Глава 2: Оценка «на салфетке» (Back-of-the-Envelope Estimation)

## Введение
Оценка «на салфетке» (back-of-the-envelope estimation) — важнейший навык на собеседованиях по системному дизайну. Это быстрые, грубые вычисления, позволяющие оценить ёмкость или производительность системы. По словам Джеффа Дина (Jeff Dean), Senior Fellow в Google, такие оценки помогают понять, отвечает ли дизайн требованиям, — через мысленные эксперименты и знание типичных показателей производительности.

В этой главе разбираются ключевые понятия, методики и примеры, которые помогут уверенно рассуждать о масштабируемости и делать оценки.

### Задержки, которые должен знать каждый программист
Числа задержек показывают, сколько времени занимают различные операции в вычислительных системах. Они дают представление об относительной производительности:

| Операция                          | Задержка (2020) |
|-----------------------------------|-----------------|
| Обращение к кешу L1               | 0.5 ns          |
| Обращение к кешу L2               | 7 ns            |
| Обращение к оперативной памяти    | 100 ns          |
| Случайное чтение с SSD            | 150 µs          |
| Случайный поиск на HDD            | 10 ms           |
| Round-trip внутри дата-центра     | 500 µs          |
| Между дата-центрами разных регионов | 150 ms        |

**Ключевые выводы:**
- Память быстрая, диск медленный.
- По возможности избегайте обращений к диску (disk seek).
- Сжимайте данные перед передачей через интернет, чтобы экономить пропускную способность.


---

### Показатели доступности
Высокая доступность (high availability, HA) означает минимальное время простоя. Доступность выражается в **девятках**:
- **99% (две девятки):** ~3.65 дня простоя в год
- **99.9% (три девятки):** ~8.8 часа простоя в год
- **99.99% (четыре девятки):** ~52 минуты простоя в год
- **99.999% (пять девяток):** ~5.3 минуты простоя в год
- **99.9999% (шесть девяток):** ~31.56 секунды простоя в год


Облачные провайдеры вроде Amazon, Google и Microsoft закладывают в SLA (Service Level Agreement, соглашение об уровне обслуживания) доступность **99.9% и выше**.

## Раздел 2: Пример оценки — QPS и объём хранилища для Twitter

### Допущения
- **300 миллионов активных пользователей в месяц (MAU).**
- **50% из них активны ежедневно (DAU).**
- **Среднее число твитов на пользователя в день:** 2.
- **10% твитов содержат медиа.**
- **Срок хранения данных:** 5 лет.

### Оценки
1. **Запросов в секунду (QPS):**
   - DAU = \( 300M x 50\% = 150M \)
   - QPS твитов = \( 150M x 2 твита / 24 часа / 3600 секунд = ~3500 )
   - Пиковый QPS = \( 2 x 3500 = ~7000 \)

2. **Хранилище для медиа:**
   - **Из чего складывается размер твита:**
     - `tweet_id`: 64 байта
     - `text`: 140 байт
     - `media`: 1 MB
   - **Объём медиа в день:** \( 150M x 2 x 10\% x 1MB = 30TB в день \)
   - **Объём за 5 лет:** \( 30TB x 365 x 5 = ~55PB \)

## Раздел 3: Советы по эффективной оценке

### 1. Округление и приближения
Точность не главное — важен сам процесс. Упрощайте сложные вычисления круглыми числами. Например:
- \( 99987 / 9.1 \) можно приблизить как \( 100,000 / 10 = 10,000 \).

### 2. Записывайте допущения
Чётко фиксируйте допущения, чтобы к ним можно было вернуться.

### 3. Указывайте единицы измерения
Избегайте двусмысленности: пишите `5 MB`, а не просто `5`.

### 4. Типичные задачи на оценку
- **QPS (запросов в секунду):** мера интенсивности трафика.
- **Пиковый QPS:** учёт всплесков трафика.
- **Объём хранилища:** оценка общего объёма данных.
- **Требования к кешу:** оценка объёма памяти под кеширование.
- **Число серверов:** расчёт потребности в железе исходя из нагрузки.
